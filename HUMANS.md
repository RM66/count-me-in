## О чём проект

**CountMeIn** (`https://countmein.group`) — онлайн-запись на групповые
мероприятия. Типичный сценарий: тренер по йоге, ведущий квиза или гид публикует
услугу («занятие в субботу в 10:00, 12 мест»), раздаёт ссылку — люди
бронируют места сами, без переписок и таблиц.

Три стороны:

- **Организатор** — заводит профиль, услуги и расписание, смотрит брони в
  веб-кабинете. Входит через Telegram (пароля и телефона нет вообще).
- **Гость** — заходит по публичной ссылке вида `countmein.group/{slug}`,
  выбирает слот, подтверждает личность тем же Telegram-виджетом и бронирует.
  Аккаунта у гостя нет — управление бронью идёт по секретной ссылке из
  сообщения бота.
- **Мессенджер** — главный канал уведомлений. Гостю приходит подтверждение со
  ссылкой на бронь, организатору — уведомление со ссылкой в кабинет.

Аудитория — организаторы любых групповых форматов: спорт, велнес, мастер-классы,
экскурсии, квизы, дрессура и т.д. (полный список в [README](README.md)).

## Архитектура в двух словах

Один монорепозиторий (Bun + Turborepo), по сути — **один деплой**: приложение
`apps/web` это одновременно Next.js-сайт и Python-API, собранные в один
Vercel-проект.

```
Браузер гостя/организатора
        │
        ▼
┌─────────────────────────────┐
│  Next.js (apps/web)         │  лендинг, публичные страницы, кабинет,
│  React + Tailwind + shadcn  │  Auth.js-сессия, SSR-чтения
└───────┬─────────────────────┘
        │ HTTP /api/*  (то же доменное имя, один origin)
        ▼
┌─────────────────────────────┐
│  Python API (FastAPI)       │  одна «толстая» Vercel-функция:
│  apps/web/api/index.py      │  все REST-эндпоинты + обработчики джоб
└──┬───────┬───────┬──────┬───┘
   │       │       │      │
   ▼       ▼       ▼      ▼
Postgres  Redis   R2     QStash ──► POST /api/jobs/{queue} ──► Telegram-бот
данные    тикеты, картинки очередь     (QStash сам дёргает API обратно)
          rate-   (аватар,
          лимит   фото услуг)
```

Почему так: на Vercel нельзя держать постоянный фоновый процесс-воркер, поэтому
вместо классической очереди — Upstash QStash: API после транзакции публикует
задачу в QStash, а QStash сам дёргает API обратно с подписью. Отдельный
случай — Auth.js: он живёт в Next.js навсегда (это его дом), поэтому
аутентификация сессии — единственное, что API не забрал себе целиком.

## Как модули взаимодействуют

- **Браузер → API напрямую.** Клиентский слой `src/api-client/` (React Query)
  ходит на same-origin пути `/api/*`. На Vercel `vercel.json` переписывает их
  на функцию `api/index.py`, в dev-режиме `next.config.js` проксирует на
  локальный uvicorn (`:3001`).
- **SSR → API тоже по HTTP.** Next.js не трогает Postgres вообще — ни одного
  прямого запроса. Серверные компоненты читают данные через
  `src/server/api-client.ts`, подписываясь заголовком `X-Organizer-Auth`
  (короткоживущий JWT из сессии) или сервисным секретом `x-internal-secret`.
- **API → Postgres.** SQLAlchemy 2.0, схемой владеет Alembic
  (`apps/web/alembic`, один baseline `0001`).
- **API → Redis.** Одноразовые гостевые тикеты, логин-ссылки, rate-limit.
- **API → R2.** Клиент уменьшает картинку в браузере → просит у API
  подписанный URL → грузит напрямую в R2 → сохраняет только ссылку.
- **API → QStash → API.** Бронирование коммитится → в той же транзакции
  пишется строка в outbox → после коммита API публикует её в QStash →
  QStash доставляет на `POST /api/jobs/{queue}` → обработчик шлёт
  Telegram-сообщение. Если QStash упал между коммитом и публикацией —
  планировщик-свипер допубликует зависшие строки.
- **`packages/contracts` — единый источник правды** по всему, что ходит по
  проводу: Zod-схемы + манифест роутов. Из них генерируется OpenAPI-спека, а
  из неё — Python-модели и правила валидации (см. ниже).
- **`packages/translations` — все тексты** интерфейса и уведомлений
  (ICU-сообщения по локалям).

## Бэкенд подробнее

Весь API — один FastAPI-процесс (`api/index.py` отдаёт приложение из
`api/_lib/countmein/`). Одна функция на все роуты — один холодный старт на
всё, а не по функции на эндпоинт.

Слои строго в одну сторону:

```
routes/        HTTP-граница: декодирование запроса, auth-гварды,
               проекция доменных данных в wire-формат (to_*_record)
   │
services/      бизнес-инварианты, транзакции, outbox, demo-гварды;
   │           возвращают только доменные снапшоты (*Row)
   │
repositories/  чистые запросы SQLAlchemy, без бизнес-логики
   │
models/        декларативные модели + Alembic (владелец схемы)
```

Важные детали:

- **Валидация запросов — сама OpenAPI-спека.** Внутрь функции вшит
  `spec_gen.json`: трансформации → jsonschema по спеке → объявленные
  правила → готовый DTO. Сгенерированные файлы (`*_gen.py`) руками не
  правят никогда — меняют источник и перегенерируют (`bun run generate:py`).
- **Outbox-паттерн.** Уведомление — это строка в `notification_outbox`,
  вставленная в той же транзакции, что и бронь. Публикация после коммита,
  дедупликация по id строки, потребитель помечает обработку в Redis —
  «хотя бы раз» без дублей на практике.
- **Умная деградация.** Redis недоступен → rate-limit пропускает запрос
  (лучше открытая дверь, чем лежащий сайт — защита от абьюза не должна стать
  точкой отказа), но событие пишется в лог. QStash недоступен → бронь всё
  равно успешна, свипер догонит.
- **Холодный старт под контролем.** Ленивые синглтоны, `boto3`/`qstash`
  подтягиваются только где нужны, отдельный тест проверяет, что импорт
  приложения не тащит тяжёлые зависимости.
- **Двойной рантайм.** На Vercel — `NullPool` без пула соединений; в
  контейнере (Dockerfile + docker-compose, локально или AWS) — обычный
  пул. Одна кодовая база, два режима.

## Фронтенд подробнее

Next.js App Router, весь исходник под `apps/web/src/`:

- **`server/` — серверная половина «провода»** (SSR-чтения, Auth.js,
  разрешение «чей это кабинет», сервисный секрет). Каждый файл помечен
  `import 'server-only'` — попытка импортировать из клиента ломает сборку.
- **`api-client/` — браузерная половина «провода»**: по файлу на сущность,
  React Query, централизованная фабрика ключей кеша (`keys.ts` — чтобы
  инвалидация кеша не разъезжалась).
- **`app/` — страницы**: лендинг, `/{slug}` и `/{slug}/{serviceId}` для
  гостей, `/cabinet/*` для организатора, `/booking/{token}` — управление
  бронью гостя, `/login`, `/signup`.
- **UI:** shadcn/ui (Radix) + Tailwind, TanStack Query для серверных данных.
- **`proxy.ts` — это middleware** (Auth.js): в Next 16 он называется так и
  ищется строго в корне `src/` — перенос молча отключает авторизацию без
  ошибок сборки. Не трогать.
- **В кабинете:** услуги, слоты, недельный календарь, брони, аналитика
  заполняемости, настройки профиля.

## Важные моменты

**Контракты.** `packages/contracts` — единственное место, где описано, что
ходит по проводу. Добавить поле/роут = изменить манифест →
`bun run generate:py` → спека, Python-модели, константы, правила и
переводы перегенерируются. Расхождение спеки с хендлерами — красный CI.
Ручного кодогена нет: `*_gen.py` — read-only. Готовую спеку можно
полистать в GUI: `bun run docs:api` поднимает локальный Scalar.

**Авторизация — только мессенджер.** Ни паролей, ни телефонов, ни OTP.
Telegram Login Widget отдаёт подписанный HMAC-payload, сервер проверяет подпись.
Организатор получает Auth.js-сессию; гость — одноразовый короткоживущий
тикет (Redis), который «сгорает» при бронировании — подделать `messengerId`
с клиента нельзя. Ссылки в уведомлениях организатору — одноразовые
логин-ссылки, потребляются только через POST (превью-боты мессенджеров не
должны их сжигать).

**Локализация.** 8 языков; выбор едет в куке `NEXT_LOCALE`, потом
`Accept-Language`, потом английский. Язык **не** в URL — все когда-либо
разосланные ссылки остаются валидными. Каждому — свой язык: организатору
уведомления на `organizers.language`, гостю — на локали, в которой он
бронировал (`bookings.guest_locale`). Все видимые строки — только через
словари, хардкод запрещён ESLint-правилом. Арабский рендерится справа
налево (`dir="rtl"`).

**Таймзоны.** Слот хранится как абсолютный момент (`timestamptz`), но
организатор вводит его по своему местному времени — зона живёт на
организаторе (`Organizer.timezone`), конвертация в обе стороны — в
`packages/contracts`. Отображение всегда в зоне организатора, меняется
только язык подписей.

**Защита от овербукинга.** Места бронируются одним атомарным UPDATE:
`SET booked_count = booked_count + :seats WHERE booked_count + :seats <= capacity`.
Если строка не обновилась — мест нет. Никаких «прочитал → проверил →
записал» на уровне приложения. Плюс частичный уникальный индекс: один гость —
одна активная бронь на слот.

**Управление бронью гостем.** `manageToken` — секретная ссылка
`/booking/{token}` из сообщения бота. В БД — SHA-256-хеш (утечка дампа не
отдаёт живые ссылки); сырой токен нужен только чтобы перевыпустить ссылку.
Токен истекает через 24 часа после начала слота — бронь остаётся в истории,
но кнопка отмены скрывается. Отмена — гостем по ссылке или организатором из
кабинета, одной транзакцией с возвратом мест.

**Демо.** `/demo` — настоящий организатор с посеянными данными: пример
страницы показывает боевой путь чтения, а не мок. Кабинет открыт анонимно:
залогиненный видит своё, остальные — демо только для чтения. Все пути
записи отвечают `403 demo_read_only`, уведомления для демо не отправляются
никогда, сид обновляется ежедневно по расписанию QStash.

**Безопасность периметра.** API — same-origin: CORS-заголовков нет вообще,
защита от CSRF — сам дизайн креденшелов (нужные заголовки/токены
кросс-сайт страница физически не получит). Слот или услугу с хоть одной
бронью (даже отменённой) удалить нельзя — 409, брони это история гостей.
Старые картинки в R2 чистятся best-effort после коммита.

## Деплой и разработка

**Прод — Vercel, один проект** с корнем `apps/web/`: Next.js собирается как
обычно, Python-функция — `api/index.py` (`vercel.json` rewrites ведут
`/api/*` на неё, `maxDuration` 10с). Postgres и Redis — через интеграции
(Supabase/Upstash). Расписания QStash (ежедневный demo-refresh и свипер
outbox) живут в Upstash и синхронизируются скриптом `ensure-qstash.ts` из
CI при каждом пуше в master.

**Локально:**

```sh
bun install && uv sync          # JS + Python зависимости
docker compose up postgres redis
bun run db:migrate:py           # alembic upgrade head
bun run db:seed:demo            # засеять /demo
bun run dev                     # Next :3000 + API (uvicorn) :3001
```

`docker compose up -d` поднимает и полный стек в контейнерах — тот же
образ, что годится для AWS ECS/App Runner.

**Тесты — три отдельных стека:**

```sh
bun run test      # Vitest (TS, юнит + компоненты)
bun run test:py   # pytest (Python API; нужны живые Postgres + Redis)
bun run test:e2e  # Playwright: 3 сценария — бронь гостя, создание в кабинете, demo read-only
```

Плюс `bun run lint:py` (ruff + mypy --strict) и `bun run generate:py` после
любого изменения контрактов.
