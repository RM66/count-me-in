# ADR-011: Localization — cookie-based locale, next-intl, EN + RU + ES

**Status:** Accepted
**Date:** 2026-08-18
**Deciders:** Product, Engineering

## Context

Every page and every notification was hardcoded English: ~150 TSX files of UI copy, four
Telegram templates in the worker, and date formatting pinned to `en-US`/`en-GB`. The target
audience includes Russian-speaking organizers and guests, and the `LanguageSwitcher` was already
seeded into every section header as a placeholder with no wiring behind it.

The public URL space is load-bearing: public pages live at `/{orgSlug}`, deep links at
`/login/link/{token}` and `/booking/{manageToken}`, and those links are minted by the worker and
shared inside messengers. Any scheme that changes the shape of these URLs has to keep every
previously sent link working.

## Decision

1. **Locale is not part of the URL.** The same route serves every language; the choice travels
   in the `NEXT_LOCALE` cookie, falling back to the `Accept-Language` header and then to
   English. Resolution order per request: cookie → header → `en`. This keeps `/{orgSlug}` at the
   root (no `[locale]` segment to fight the dynamic slug and the reserved-slugs list) and every
   deep link ever sent remains valid. The trade-off — no per-language URLs for SEO — is accepted
   for a product distributed through messengers, not search.

2. **next-intl is the i18n engine**, in both apps: `apps/web` uses the request-config +
   `NextIntlClientProvider` / `getTranslations` / `useTranslations` split; `apps/worker` uses the
   framework-free `createTranslator` core. ICU messages give correct pluralization for both
   singular and plural forms in every supported language without hand-rolled rules (RU has three
   plural forms).

3. **Languages: English (default, fallback), Russian, and Spanish.** The supported set is a single
   `LOCALES` constant in `packages/contracts/src/i18n.ts`, shared so web and worker cannot
   disagree about what a locale string is. `matchLocale` maps `Accept-Language`-shaped input to
   that set and is reused by the signup form's browser detection.

4. **Public pages follow the viewer's language** (cookie/header), like the rest of the site.
   The cabinet UI does the same; the landing/cabinet/marketing copy migration is a later
   iteration.

5. **Notifications are per-person.** The organizer receives messages in `organizers.language`
   (initialized at signup from the browser locale, English default; afterwards the language
   switcher owns it — switching while signed in updates the column alongside the cookie, so
   interface language and notification language are one setting); the guest receives messages
   in `bookings.guest_locale` (captured from the active UI locale when the booking is created,
   English default). The worker resolves the locale at send time from the freshly refetched
   rows — jobs still carry ids only. Unknown stored values fall back to English.

6. **Times keep rendering in the organizer's timezone** (docs/domain.md) — only the labels
   (weekday/month names, number formats) follow the locale. Wall-clock output must not move.

## Consequences

- All pages become dynamic (the request config reads cookies/headers); this is already true for
  every data-driven route and is an accepted cost for the landing page.
- English remains the source of truth for message *shape*: every translated dictionary must mirror
  the English keys (parity tests in the package enforce it), and all dictionaries live as ICU
  JSON in `packages/translations` — `messages/` for the web UI, `notifications/` for the worker.
  TypeScript infers JSON module types with literal keys, which is what type-checks every `t()`
  call and the web's `IntlMessages` augmentation without a code generator.
- Two new columns (`organizers.language`, `bookings.guest_locale`, both `text DEFAULT 'en'`).
  Client-side errors with server payloads (`seatsLeft`, `maxSeats`) are re-rendered locally
  instead of showing the server's English copy.
- Telegram templates keep their HTML in code, not in ICU messages — use-intl reads `<b>` tag
  pairs as rich-text placeholders, which is the wrong tool for Telegram HTML.
- Rollout: infrastructure + guest booking flow + worker notifications shipped first; cabinet,
  marketing, auth, legal and the landing followed. Server-side API errors are localized too —
  route handlers and request-scoped helpers resolve the `ApiErrors` dictionary via
  `getTranslations`, error *classes* keep English `message`s for logs. api-client has no locale,
  so its last-resort fallbacks stay as named English constants (documented as such) — the
  display site translates whatever the server sends.
