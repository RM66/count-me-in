## 2. Принципы отбора (что тестируем, что нет)

1. **Инварианты и безопасность первее UI.** Места (`UPDATE … WHERE bookedCount + :seats <= capacity`), отмена (идемпотентность `status='confirmed'`), `manageToken` только через SHA-256 хеш, single-use тикеты, demo read-only на **каждом** write-пути, `booking.created` fan-out по одному job на получателя — это P0. Ошибка здесь = овербукинг, утечка чужих броней, спам.
2. **Не тестируем:** `components/ui/*` (shadcn/Radix, покрыты апстримом + Storybook), `app/(marketing)/*`, OG-картинки (кроме `assets.ts`), `*.stories.tsx`, `pkg/api/gen/*` (oapi-codegen), тонкие синглтоны (`redis/client`, `db/client`, `logx`, `posthog`, `seo`).
3. **Чистые функции — unit, транзакции — integration.** `templates.go`, `demo/guard`, `week-layout`, `compute-analytics`, `image downscale` — unit без моков. `booking_writes`, `routes/*`, `jobs/*_created` — только реальный Postgres (+ Redis для тикетов), моки скрывают класс багов из `booking.integration.test.ts` (Drizzle cache + `Buffer.from(Date)`).
4. **Одна проверка — один инвариант из `docs/domain.md` / ADR.** Тест называется по инварианту (`002-guest-booking`, `010-demo`, `011-i18n`, `012-queue`, `020-manage-token-hash`), а не по функции.

## 4. Порядок запуска (что делать первым)

1. **P0-2 + P0-3** (demo/ticket/loginlink/guards) — 0.5–1 день, чистые функции + miniredis, закрывают дыру «аноним пишет как организатор» и «replay тикета».
2. **P0-4 + P0-6** (run/dispatch + error mapping) — 1 день, table-driven без DB, фиксируют семантику 400 vs 500 (деньги QStash-ретраев).
3. **P1-1** (templates, 8 локалей) — 1–2 дня, golden-файлы; каждый неотловленный XSS/плюрал = 400 от Telegram и непонимание пользователя.
4. **P0-1 + P0-5** (booking_writes + routes bookings) — 2–4 дня, требуют test-DB; ядро продукта (овербукинг/идемпотентность/outbox).
5. **P1-2 + P1-3** (handlers + outbox sweep) — 2 дня, fake Telegram + test-DB.
6. **P1-5 → P1-9** (фронт) — по 0.5 дня на файл, параллельно с бэком.
7. **Infra-1 → Infra-3 + E2E smoke** — включить гейты, перестать скипать integration.

Явно **не** делать: покрытие ради процента по `ui/`, `(marketing)/`, `gen/`; snapshot-тесты страниц целиком; моки `UPDATE … WHERE` логики в JS (только реальный Postgres).

## 5. Критерии готовности

- P0+P1-Go закрыты: `pkg/demo` 100%, `pkg/config` 100%, `pkg/queue` ≥ 90%, `pkg/auth` ≥ 85%, `pkg/jobs` ≥ 80%, `pkg/httpx` ≥ 60%, `pkg/storage` ≥ 50%, `pkg/db` ≥ 30% с БД (service/timeslot/organizer reads — остаток), `pkg/routes` ≥ 20% с БД (CRUD organizers/services/slots — остаток).
- Ноль `skip` в CI: integration-тесты ходят против сервисов workflow (`requirePostgres` падает при `CI=true` без БД).
- `bun run test` зелёный одной командой (turbo `test` уже зависит от `generate:*` — не сломать).
- Каждый новый write-route приходит с парой тестов: happy path + demo/refusal; каждое новое job-сообщение — с golden на 8 локалей.
