# Discrepancies: plan vs Go code (Phase 1)

Rule 0.2: when the plan and the Go code disagree, the Go code wins. **Resolution rule:** a discrepancy is _ported as-is_ to Python — byte-compatible behavior is the goal of the migration, so an oddity in Go becomes an explicit, tested oddity in Python. It is recorded here, and any deliberate fix happens after the Phase 6 cutover, on both sides or in the spec, never mid-migration. Each entry records what the plan claims, what the code does, and the resolution adopted.

1. **Spec operation count.** Plan §1.2 says "Expected count at baseline: 25 spec operations + healthz". Actual `openapi.yaml` at baseline has **23** operations; the plan's own breakdown (auth ×2, organizers ×6, services ×5, slots ×5, bookings ×4, jobs ×1) sums to 23. Resolution: 23 is correct; `check-inventory.ts` asserts 23.
2. **Rate limits enforced in code but absent from the route manifest.** `routes.ts` documents `rateLimit` only for telegramGuest, telegramSignup, createBooking, and the two upload-target endpoints. The Go handlers additionally enforce:
   - `POST /api/organizers` — `rl:register:<ip>` 10/hour (`organizers.go:31`)
   - `POST /api/bookings/lookup` — `rl:lookup:<ip>` 10/min (`bookings.go:123`)
   - `POST /api/bookings/cancel` — `rl:cancel:<ip>` 10/min (`bookings.go:167`)
     Resolution: Python ports the Go behavior (enforced limits); the manifest/spec stays untouched — the spec documents a subset, which is its stated intent ("Documented for the spec and for the 429 response; enforcement is in the handler").
3. **`GET /api/healthz` is not in the spec** by design (mounted in `pkg/api/server.go` outside the generated router). Plan §1.2 already accounts for this; recorded here so the Python side mounts it outside the OpenAPI-derived route set too.
4. **FlexTime rejects date-only strings by design; Zod's `coerce.date()` accepts them.** The `date-only startsAt` vector cases (CreateTimeSlotInput, UpdateTimeSlotInput) were recorded as `valid: true` with a `skip.go` — a silent hole in the Go/Python vector runs. Resolution: the API stacks are the contract — the cases are now `valid: false` with a `skip.ts` (Zod's acceptance of date-only is the outlier, local-midnight parsing being exactly what the API must not do), and both the Go and Python vector runs assert the rejection. A deliberate Zod-side fix (if ever) happens after the Phase 6 cutover, on both sides or in the spec.
5. **Log line `time` format differs from Go.** Go's `slog.NewJSONHandler` renders `time` as RFC3339 with nanosecond precision and a local offset (e.g. `2026-09-26T22:15:04.123456789+02:00`); the Python port renders millisecond precision in UTC (`2026-09-26T22:15:04.123Z`). The `level` names match slog exactly (uppercase `INFO`/`WARN`/`ERROR`). Resolution: ported as-is (UTC milliseconds) — the field is a timestamp either way, drains parse both, and no consumer pins the format; a deliberate unification happens after the Phase 6 cutover if a drain ever needs it.
6. **Access log for `/api/healthz`.** Production Go writes no access log at all — every request line in the review came from `cmd/dev`'s dev-only wrapper. The Python middleware adds a per-request access log (plan §4.1 requires one) and excludes healthz from it, matching the one Go behavior that exists on this point (healthz never reaches a request logger in production). Resolution: the access log itself is a Python-side addition per §4.1; the healthz exclusion is ported from production Go.
7. **Healthz panic scope.** Go's probe panics on any client-initialization error — an empty `POSTGRES_URL` (the lazy engine raises) but also e.g. an unparseable `REDIS_URL` — and `Recover` answers the full-failure 503. The Python port reproduces the panic path only for the empty-`POSTGRES_URL` case (the common misconfiguration, and the one Go's own test pins); other init errors surface as an ordinary per-dependency `"fail"` in the 200/503 body. Resolution: ported as-is; the narrower scope is deliberate — a malformed `REDIS_URL` still answers 503 with `redis: "fail"`, only without the panic-shaped body. A deliberate widening happens after the Phase 6 cutover if a drain ever needs the distinction.
